# Round 001：不同模型失败原因分析

## 1. 分析目标与证据边界

本轮首先解释 Phase 05 中不同模型为什么没有通过全部 51 条冻结评估用例，并为后续数据集重构提供依据。本文件只记录现象、证据、原因假设和待确认事项；尚未批准数据修改、训练策略或实验变体。

证据来自：

- `reports/phase05/report.md` 的统一汇总；
- `reports/phase05/<model-id>/quality.json` 的逐样本期望、实际输出、得分和错误标签；
- `data/eval/test.jsonl` 的冻结评估合同；
- `data/processed/sft/v0.1/` 与 `data/processed/dpo/v0.1/` 的训练目标；
- 当前任务正确性与回复语义评分代码。

当前评估集只有 51 条，因此可以定位明确失败模式，但暂时不能把每个切片的通过率当作稳定总体概率。

## 2. 模型总体表现

| 模型 | 协议遵循 | 任务正确性 | 有效通过 |
|---|---:|---:|---:|
| 0.6B Base Q4 | 68.6% | 43.2% | 2/51 |
| 0.6B SFT Q4 | 78.4% | 78.3% | 22/51 |
| 0.6B DPO-b01 Q4 | 86.3% | 79.7% | 24/51 |
| 0.6B DPO-b03 Q4 | 80.4% | 77.0% | 23/51 |
| 0.6B SFT F16 | 86.3% | 81.7% | 25/51 |
| 1.7B Base Q4 | 68.6% | 58.1% | 7/51 |
| 1.7B SFT Q4 | 94.1% | 91.9% | 29/51 |
| 1.7B DPO-b01 Q4 | 96.1% | 90.5% | 30/51 |
| 1.7B DPO-b03 Q4 | 92.2% | 92.1% | 29/51 |
| 1.7B SFT F16 | 88.2% | 91.8% | 29/51 |

SFT 相对 Base 带来显著提升，证明训练方向有效。1.7B 普遍优于 0.6B，说明模型容量影响复杂状态处理和结构稳定性。DPO 只带来小幅且不稳定的变化；Q4 相对 F16 在 0.6B 上有一定损失，但不是大多数失败的来源。

## 3. P001：多轮状态继承与局部修改不稳定

0.6B SFT Q4 在单轮样本中通过 13/23，在多轮样本中仅通过 9/28；多轮平均任务正确性约为 0.725。主要表现为：

- 用户只修改一个条件时，模型同时覆盖其他字段；
- 更换技师后没有正确保留时间和时长；
- 修改时间或偏好后没有使旧工具结果失效并重新查询；
- 从历史和 `current_state` 合并状态时使用了错误日期或旧值；
- 把 `technician_name` 当成预约必填字段，产生错误追问。

例如 `multiturn-time-01-call` 期望时间为 `2026-06-10 10:00`，0.6B SFT Q4 输出为 `2026-07-05 10:00`。`multiturn-pref-01-call` 本应重新调用工具，模型却输出 Final 并追问技师姓名。

1.7B SFT Q4 的多轮通过数提高到 13/28，但同样在修改时间、偏好、工具结果确认等边界失败。因此这不是 0.6B 独有问题，而是同一数据和任务设计在小模型上暴露得更严重。

最可能原因是：现有数据包含多轮记录，但对“旧状态 + 当前修改 → 新状态 + 动作”的状态差分规律覆盖和强化不足，尤其缺少组合修改、反事实近邻以及保持未修改字段不变的对照。

## 4. P002：工具调用参数和调用时机错误

0.6B SFT Q4 的 15 条 Tool Call 仅通过 4 条，平均任务正确性约 0.686；至少 9 条失败样本包含工具参数错误。高频问题包括：

- `start_time` 日期或小时错误；
- `technician_name` 被丢失；
- 将泛化词“按摩”写入本应为空的 `preferences`；
- 将“泰式”改写为“泰式按摩”，在严格参数比较下失败；
- 用户更新条件后没有继承未修改参数；
- 信息完整时仍继续追问，而不是调用工具；
- Tool Call 内混入 Final 专属字段。

1.7B 也存在同类问题，例如指定技师请求中擅自加入 `[按摩]` 或 `[按摩, 身体部位：腿部]`。这说明问题不仅是参数规模，也包含训练目标对偏好规范化边界定义不足。

最可能原因是模型同时承担了自然语言理解、时间归一化、状态合并、动作决策和严格 Schema 生成，而工具调用类训练目标仅占 SFT 训练集 97/450。是否单纯提高比例即可解决，仍需通过对照实验确认。

## 5. P003：JSON 和 Schema 稳定性不足

0.6B SFT Q4 有 11 条协议失败，其中包括：

- 5 条不可解析输出；
- 非正整数 `duration_minutes`；
- 非法 `start_time` 格式；
- 不支持的 `technician_status`；
- `missing_info` 包含不允许字段。

同一模型的 F16 版本协议失败降至 7 条；1.7B SFT Q4 仅有 3 条协议失败。模型容量和量化都会影响格式稳定性，但 0.6B F16 仍有明显失败，说明训练数据中的协议强化和错误边界覆盖同样不足。

## 6. P004：回复语义与 0.95 门槛造成临界失败

0.6B SFT Q4 的 29 条失败中：

- 11 条是协议失败；
- 10 条协议正确，任务分处于 0.90 至 0.95；
- 5 条协议正确，任务分处于 0.80 至 0.90；
- 3 条协议正确但低于 0.80。

因此“22/51”把严重结构错误和接近正确的表达问题压缩成了同一个失败标签。

例如 `specific-available-01-confirm` 的结构化字段全部正确，模型回复“已确认预约……为您安排”，原评估却要求表达“正在办理预约”。经人工确认，当前业务把“技师已核实可用 + 用户明确确认”直接定义为预约成功，因此该样本属于评测误报，已在评估合同 v2.4 中修正。其余临界失败仍需逐条区分真实错误和评分误伤。

## 7. P005：训练与评估合同存在明确冲突

SFT v0.1 中：

- 训练集 50 条 `acknowledge_result` 全部为 `confirmation=false`；
- 验证集 3 条 `acknowledge_result` 也全部为 `confirmation=false`。

但 eval-v0.1 中以下三条曾要求 `acknowledge_result` 同时为 `confirmation=true`：

- `specific-unavailable-01-confirm`；
- `specific-not-found-01-confirm`；
- `search-no-match-01-confirm`。

0.6B 和 1.7B 后训练模型均稳定输出 `false` 并被扣分。模型行为符合训练合同，却不符合旧评估合同。当前已统一定义：只有用户接受已核实可用的方案时 `confirmation=true`；知悉失败结果仍为 `false`。上述三条已在 eval-v0.2 修正。

## 8. P006：DPO 和量化不是当前第一原因

0.6B SFT F16 通过 25/51，SFT Q4 通过 22/51。两者共同失败 25 条，仅有 4 条是 F16 通过而 Q4 失败，因此量化贡献了一部分损失，但无法解释主要失败集合。

0.6B 两个 DPO Q4 分别通过 24/51 和 23/51，没有稳定超过 SFT F16。DPO 后 `wrong_argument` 仍然是最高频错误，表明现有偏好对没有直接解决状态继承、参数精确复制和 Schema 稳定性。

现阶段更合理的因果顺序是：先统一任务与评估合同，再重构针对性 SFT 数据；之后才评估新的 DPO 偏好对和量化方案的边际价值。

## 9. 代表性错误案例

以下案例不是根据错误标签推测，而是直接对照同一测试样本的输入、期望输出和模型实际输出。为便于阅读，仅展示决定性字段。

### 案例 1：信息不完整时过早调用工具

样本：`ask-0001`

用户输入：

```text
我想明天下午做肩颈按摩，时长还没定
```

期望行为：下午没有具体小时，且时长缺失，因此应输出 Final，同时追问具体时间和时长：

```json
{
  "action": "final",
  "start_time": null,
  "duration_minutes": null,
  "preferences": ["肩颈"],
  "missing_info": ["start_time", "duration_minutes"],
  "reply_type": "ask_start_time_and_duration"
}
```

0.6B SFT Q4 实际行为：

```json
{
  "action": "tool_call",
  "arguments": {
    "start_time": "2026-06-09 14:00",
    "duration_minutes": null,
    "preferences": ["肩颈按摩"]
  }
}
```

具体错误：模型擅自把“下午”猜成 14:00，在时长缺失时提前调用工具，并改变了偏好标准值。1.7B 在该样本中正确选择 Final 并通过，说明这类基础决策对更大模型较容易，但 0.6B 需要更强的“信息不完整不得调用工具”训练。

### 案例 2：识别出技师和时间，却在缺少时长时丢失已有字段

样本：`ask-0005`

用户输入：

```text
想找王芳明天下午两点按摩，时长没定
```

期望关键字段：

```json
{
  "action": "final",
  "technician_name": "王芳",
  "start_time": "2026-06-09 14:00",
  "duration_minutes": null,
  "preferences": [],
  "missing_info": ["duration_minutes"],
  "reply_type": "ask_duration"
}
```

0.6B SFT Q4 错误地提前调用工具，同时输出 `technician_name=null` 和 `preferences=["按摩"]`。1.7B 虽然选择了 Final，却仍丢失王芳和已明确的 14:00，并错误地同时追问时间与时长。

该案例证明“已知槽位必须保留、只追问真正缺失字段”是两个模型共同存在的问题，0.6B 还叠加了动作决策错误。

### 案例 3：更换技师时，0.6B 把 Final 字段塞进 Tool Call

样本：`specific-unavailable-01-reselect`

历史状态已经包含：李明、`2026-06-09 15:00`、60 分钟；用户说：

```text
那查一下王芳
```

期望工具参数：

```json
{
  "technician_name": "王芳",
  "start_time": "2026-06-09 15:00",
  "duration_minutes": 60,
  "gender_preference": null,
  "preferences": []
}
```

0.6B 保留了主要参数，但在 `arguments` 中继续生成 `technician_status`、`confirmation`、`reply_type` 和 `reply` 等 Final 字段，最终输出还缺少正确闭合，成为不可解析 JSON。1.7B 在同一案例中完全正确。

这不是业务理解完全错误，而是 0.6B 没有稳定掌握 Tool Call 与 Final 两种互斥输出结构。

### 案例 4：复杂条件搜索中的时间和性别遗漏

样本：`search-no-match-01-call`

用户输入：

```text
明天晚上八点，90分钟，找会泰式的女技师
```

期望参数为 `20:00`、90 分钟、`gender_preference=female`、`preferences=["泰式"]`。0.6B 实际输出 `19:00`，同时把性别偏好写成 `null`。1.7B 正确保留了时间和性别，且“泰式按摩”被当前偏好语义匹配器接受。

该案例更偏向 0.6B 的组合槽位抽取能力不足，而不是所有模型完全相同的错误。

### 案例 5：修改时间后，两个模型以不同方式失败

样本：`multiturn-time-01-call`

用户输入：

```text
改成后天上午十点，技师不限
```

期望：继承 60 分钟和精油偏好，将时间改为 `2026-06-10 10:00`，清空技师限制，并重新调用工具。

- 0.6B 正确选择 Tool Call，也继承了时长和偏好，但把日期算成 `2026-07-05 10:00`。
- 1.7B 正确算出 `2026-06-10 10:00`，却错误输出 Final，并追问并非必填的技师姓名。

这说明同一个失败标签背后可能是不同原因：0.6B 是时间归一化错误，1.7B 是动作决策和必填字段规则错误。新数据不能只按“该样本失败”整体复制，必须针对错误机制分别构造。

### 案例 6：完整条件下仍然追问非必填技师

样本：`multiturn-pref-01-call`

用户输入：

```text
周六上午十点，60分钟，女技师，擅长肩颈
```

期望立即调用工具，参数包含 `2026-06-13 10:00`、60、`female` 和 `["肩颈"]`，技师姓名可为空。

- 0.6B 输出 Final，认为缺少 `technician_name`，还把日期写成当前日期 `2026-06-08 10:00`。
- 1.7B 正确调用工具，但把周六算成 `2026-06-10`，并输出非标准偏好“擅长肩颈”。

该案例体现两个共性问题：模型没有始终理解“技师姓名不是必填条件”，相对星期日期换算也不稳定；0.6B 的错误层级更多。

### 案例 7：“知道了”暴露训练与评估合同冲突

样本：`specific-unavailable-01-confirm`

前文工具结果是李明不可用，用户只说：

```text
知道了
```

0.6B 和 1.7B 都输出：

```json
{
  "technician_status": "unavailable",
  "confirmation": false,
  "reply_type": "acknowledge_result",
  "reply": "好的，已知悉。"
}
```

这与 SFT v0.1 中全部 `acknowledge_result` 训练目标一致，但 eval-v0.1 期望 `confirmation=true`，因此两个模型都被判错。这里首先要修合同，而不是把模型输出当作负例重新训练。

### 案例 8：结构完全正确，原评估却错误拒绝预约成功表达

样本：`specific-available-01-confirm`

用户在技师可用后说“可以，就这样”。0.6B 和 1.7B 的结构字段均正确，包括：

```json
{
  "confirmation": true,
  "reply_type": "booking_authorized"
}
```

但两者回复都类似：

```text
好的，已确认……为您安排……
```

原评估合同要求表达“已经获得用户授权、正在办理”，因此要求类似：

```text
好的，正在为您办理预约。
```

两种模型都约得 0.902。经人工确认，本项目业务规则是：技师已核实可用且用户明确确认后，预约即成功。因此这是评测误报，不是模型错误。eval contract v2.4 已改为接受“预约成功”“已确认预约”等表达；在用户确认之前仍禁止提前声称成功。

### 案例 9：“其他不变”场景中的不同继承错误

样本：`plan-modify-time-pref-01-requery`

用户输入：

```text
改成后天下午四点，改做精油按摩，其他不变
```

期望保留王芳和 60 分钟，只把时间更新为 `2026-06-10 16:00`、偏好替换为 `["精油"]`。

- 0.6B 保留了王芳和时长，但时间仍为 14:00，并生成重复的 `preferences` 键及混合值。
- 1.7B 正确更新时间，却丢失王芳，并把旧偏好“肩颈”和新偏好“精油按摩”同时保留。

这是最典型的状态差分训练缺口：模型需要明确学习“替换哪些字段、保留哪些字段”，而不是重新生成一个看起来合理的新状态。

## 10. 当前原因判断

按照证据强度，主要原因排序如下：

1. **已修复的数据合同问题**：`acknowledge_result/confirmation` 在训练和评估中定义冲突，已在 eval-v0.2 统一。
2. **高置信度训练覆盖问题**：多轮状态差分、字段继承、条件修改后重查和工具参数构造不够稳定。
3. **高置信度模型容量问题**：相同方案下 1.7B 明显优于 0.6B，但仍保留同类型错误。
4. **高置信度协议训练问题**：0.6B 对 Tool Call/Final 边界及严格 JSON Schema 掌握不足。
5. **评分问题**：三条可用方案确认样本已确认为误报并在 eval contract v2.4 修正；其他临界失败仍待人工复核。
6. **次要量化影响**：Q4 对 0.6B 有可见损失，但不是主要根因。
7. **DPO 目标未对准核心错误**：当前 DPO 收益小且不稳定，不能替代针对性的 SFT 数据修复。

## 11. 进入策略设计前必须确认

- 明确定义 `confirmation` 字段的业务语义；
- 人工审核 10 条 `0.90–0.95` 临界失败；
- 统计原始训练数据中每种状态转换和工具调用边界的覆盖；
- 决定偏好是否采用标准化值，及“泰式”与“泰式按摩”等表达是否等价；
- 决定优先通过训练强化协议，还是同时验证约束解码；
- 在上述事项确认前，不使用 Phase 05 的所有失败样本直接生成新训练标签。
