# Phase 06 Round 007：最终分析

## 修复的测量问题

历史代码把 llama.cpp 的 `predicted_ms` 写入 `first_token_ms`。前者是完整Decode时间，不是首Token延迟。本轮改为 `stream=true`，在收到第一个非空内容片段时记录真实TTFT；同时分别保留 `prompt_ms`（Prefill）、`predicted_ms`（Decode）以及各阶段tokens/s。

本地测试关闭Prompt Cache，避免重复请求复用KV Cache导致Prefill虚低。每个模型先执行一次不计入结果的预热，然后使用8条覆盖不同长度的真实业务Prompt，每条重复3次。输入长度范围为1324–1680 tokens，8 CPU线程。

## 最终本地结果

| 指标（中位数） | Q8_0 | Q4_K_M | Q4相对Q8 |
|---|---:|---:|---:|
| 模型体积 | 609.8 MiB | 378.3 MiB | -38.0% |
| Prefill | 8286.6 ms | 5035.8 ms | -39.2% |
| Prefill速度 | 168.8 tok/s | 274.9 tok/s | +62.9% |
| 真实TTFT | 8808.4 ms | 5583.1 ms | -36.6% |
| Decode | 3143.6 ms | 2644.1 ms | -15.9% |
| Decode速度 | 30.31 tok/s | 32.15 tok/s | +6.1% |
| 端到端延迟 | 11952.7 ms | 8318.0 ms | -30.4% |
| 峰值服务RSS | 1156.4 MiB | 1129.5 MiB | -2.3% |

## 结论

真实业务请求的首要瓶颈是Prefill，而不是Decode。系统Prompt和结构约束使输入达到约1.3k–1.7k tokens；Q4将Prefill中位时间降低约39%，由此将TTFT降低约37%、端到端延迟降低约30%。Q4对真实Decode速度的提升只有约6%，因此本系统后续若继续优化体感，应优先缩短Prompt、启用可控的公共前缀缓存，而不是继续压到Q3或Q2。

质量侧的云端复评结果稳定：Q8没有丢失F16原本通过的样本，合计61/75；Q4合计59/75，且相对F16的7条主集新增失败在复评中一致。因此不能把Q4描述为无损量化。Q4是明确的性能最优方案，Q8是明确的质量最优方案。

按照阶段最初的“提升速度但不损失精度”目标，正式默认版本应选择 `Q8_0`。它相对F16体积减少约47%，Decode提升，同时维持质量；`Q4_K_M`保留为低延迟部署配置，适用于愿意接受少量稳定业务回归以换取约37% TTFT改善的场景。

若后续仍希望争取Q4速度同时恢复质量，唯一值得继续的量化实验是围绕Q4做一轮校准：使用业务代表性语料生成imatrix，并只复评已确认的7条回归加完整holdout。Q5/Q6、Q3和IQ2无需重开。
