# Phase 06 Round 006：量化矩阵分析

## 实验范围

质量评测固定最终 `r004-qwen3-0.6b-sft` 模型，在同一云端环境、同一 llama.cpp 版本、相同 GPU offload 与解码参数下运行51条主集和24条 holdout。速度评测在本地 CPU 上使用相同 Qwen3-0.6B 架构，分别测量 Prefill 与 Decode；本地速度模型不用于质量判断。

云端硬件为 RTX 4080 SUPER（32 GB）、96逻辑CPU、约504 GiB内存；本地速度环境为 AMD EPYC 7763、8推理线程。

## 结论

`Q4_K_M` 是本轮性能最好的部署候选。相对 F16，其体积减少约67%，本地 Prefill 512提升约46%，Decode 128提升约81%，合计质量只下降1条（60/75到59/75）。它也是本机上唯一同时明显改善 Prefill 与 Decode 的量化格式。

`Q8_0` 是质量安全基线。它没有丢失任何 F16 原本通过的样本，主集新增通过1条且 holdout完全一致；体积减少约47%，Decode提升约45%，但本机 Prefill下降约20%。

在本次模型、量化工具版本、硬件和评测集上，`Q4_K_M` 支配 `Q5_K_M`：Q4更小（378 MiB对424 MiB）、Prefill和Decode更快，合计通过数也略高（59/75对58/75）。这不表示4-bit天然比5-bit精度更高。任务通过率是离散指标，75条样本中一两条边界变化就会改变排序；不同量化误差也可能分别修复或破坏不同样本；`K_M`还是按张量采用不同精度的混合方案，而不是全模型统一4位或5位。

`Q6_K`与`Q5_K_M`在本轮没有提供相对Q4的质量或速度优势，可以淘汰。`Q3_K_M`已出现明显能力崩塌；`IQ2_M`和`IQ2_XS`产生重复字段、错误参数和截断JSON，质量完全失效，速度也没有超过Q4，因此本轮停止3-bit和2-bit路线。

云端 `first_token_ms` 当前仍是错误命名的完整 Decode 时间，不是真实 TTFT；IQ2还频繁生成到长度上限。因此云端延迟不用于速度排序，本轮速度结论只采用本地 llama-bench 的 Prefill/Decode数据。

## 下一步

第二轮只保留 `Q8_0` 与 `Q4_K_M`，不再重复八档全矩阵：

1. 对Q4相对F16新增失败的7条主集样本进行定向复评，同时保留Q4新增通过的4条样本，确认变化是否稳定、是否属于评分阈值摆动。
2. 使用同一云端环境分别重复运行Q4和Q8至少两次。Q8用于确认无损参考，Q4用于确认业务回归风险；不依靠一次75条总分直接定版。
3. 修复真实流式TTFT测量，在本地使用最终Round 004合并权重，对Q4和Q8运行代表性短、中、长请求，记录TTFT、端到端延迟和峰值内存。
4. 若Q4的关键业务回归稳定存在，选择Q8作为稳健部署版本；若回归主要是非关键边界样本或不可稳定复现，则选择Q4作为最终部署版本。

当前不建议立即做 imatrix 或混合精度优化。第一优先级是确认Q4的7条新增回归是否真实稳定；只有确认其中存在少量、稳定且重要的回归后，才值得围绕Q4尝试改进量化校准。
